# 작업 파일 수집 (IDX-3-02)

2026-11-10 (Asia/Seoul), S15P31D108-186. 브로커가 바인딩된 프로젝트의 미커밋 파일 목록을 중앙에 반영한다. 담당 Agent 탐색(FIND-3-01)은 이 관측으로 "작업 중" 근거를 계산한다. 업로드 본문은 [Git 수집 범위 제한](git-collection-scope.md)의 `WorkingFiles`로 만든다.

## 동작

- 브로커가 시작될 때 바인딩된 Agent 프로필이 있으면 수집기를 시작한다. 프로젝트가 Git 저장소가 아니거나, 원격을 찾지 못하거나, 지원하지 않는 원격 형식이면 시작할 때 한 번 알리고 수집하지 않는다.
- 원격은 `dependencyRemote` 설정값을 쓰고, 비어 있으면 `origin`을 쓴다. 저장소 키는 팀 의존성 분석과 같은 규칙(정규화한 원격 URL의 SHA-256)이다. 호스트만 소문자로 바꾸고 경로의 대소문자는 유지한다.
- 3초마다 `git status --porcelain=v1 -z --untracked-files=all --no-renames`를 읽는다. 마지막으로 중앙이 받은 목록과 다르면 바로 `PUT /api/v1/teams/{teamId}/git/working-files/{repoKey}`로 전체 목록을 교체한다. 그래서 의존성 트리의 "작업 중" 표시가 약 3초 안에 바뀐다.
- 목록이 같아도 마지막 성공 전송 후 30초가 지나면 다시 보낸다. 중앙은 받은 시각부터 90초가 지나면 관측을 만료한다. 전송이 실패하면 직전 성공 기록을 비워, 목록이 이전 상태로 돌아가도 다음 확인에 다시 보낸다.
- 중앙이 바인딩된 Agent·사용자·팀으로 연결된 상태(Connected, 신원 일치)일 때만 보낸다. 주기 확인과 탐색 직전 확인은 단일 수집기가 순서대로 처리한다. 탐색 호출자가 대기를 취소해도 이미 시작한 전송은 HTTP 응답 또는 HTTP 제한 시간까지 유지한다.
- 빈 목록도 관측으로 보낸다. 분리된 HEAD, UTF-8로 해석할 수 없는 브랜치, 중앙 규칙(문자·숫자·`._/-`, 255코드포인트 이하, `-` 시작·`..` 금지)에 맞지 않는 브랜치는 `branch: null`로 보낸다.
- 중앙 경로 규칙에 맞지 않는 파일 경로는 건너뛴다. 작업 파일은 500코드포인트와 UTF-8 1,000바이트 한도를 모두 만족해야 한다. 초과 경로만 제외하고 나머지 정상 경로는 계속 수집한다. 수집 가능한 변경 파일이 2,000개를 넘으면 그 주기에는 보내지 않고, 이전 관측은 만료된다.
- 업로드가 실패하면 연속 실패 중 한 번만 stderr에 알리고 다음 주기에 다시 보낸다.

## 조건부 저장 (revision)

중앙 작업 파일 protocol 2(DevLink_server #96)를 따른다. 늦게 처리된 이전 요청이 최신 목록을 덮지 못하게 한다(F8).

- 3초 확인에서 목록이 마지막 성공 목록과 같고 30초가 지나지 않았으면 중앙에 아무 요청도 보내지 않는다.
- 보낼 때는 **매번** 먼저 `GET /api/v1/teams/{teamId}/git/working-files/{repoKey}`로 revision을 받는다. 응답은 `{"protocolVersion": 2, "revision": "<UUID>"}`다. 그다음 Git을 다시 읽어 본문을 만들고 `If-Match: "<revision>"`을 붙여 `PUT`한다. 성공 응답에 protocol 2 revision이 없으면 실패로 처리한다.
- 성공 응답의 revision은 다음 업로드에 재사용하지 않는다. 실행 중 중앙이 revision을 지원하지 않는 버전으로 롤백되면 그 버전은 `If-Match`를 무시하고 저장하기 때문이다. 매번 조회하면 롤백된 중앙에서는 조회가 실패하므로 `PUT`을 보내지 않는다. 조회와 `PUT` 사이(수 ms)에 롤백되는 경우만 남는다.
- 요청을 보내기 직전에 마지막 성공 목록을 비운다. 타임아웃·연결 끊김·오류 응답이면 다음 시도가 revision을 다시 조회하고 Git도 다시 읽는다. 이전 본문에 새 revision을 붙여 다시 보내지 않는다.
- `412 WORKING_FILES_REVISION_MISMATCH`이면 다른 쓰기가 먼저 반영된 것이다. 같은 호출 안에서 revision 조회와 Git 읽기를 한 번 더 하고 다시 보낸다. 다시 충돌하면 실패로 처리하고 다음 주기에 처음부터 한다.
- revision을 주지 않는 중앙(조회 경로 없음, `protocolVersion`이 2가 아님, revision 형식 오류)에는 보내지 않는다. 보호 없는 업로드로 되돌아가지 않는다. 그래서 이 CLI보다 중앙 #96이 먼저 배포되어 있어야 하고, 롤백된 중앙에서는 작업 파일 관측이 90초 뒤 만료된다.
- 같은 사용자의 여러 Agent·PC는 같은 revision을 공유한다. 서로의 쓰기가 충돌로 감지되어 다시 조회하며, 마지막 관측이 남는 정책은 그대로다.

## 탐색 직전 재확인

`find_agent`(`/v1/agents/find`)는 세션 확인 뒤 중앙 추천을 요청하기 전에 작업 파일을 한 번 더 보낸다. 3초 안에 끝나지 않거나 실패해도 탐색은 계속하며, 중앙은 아직 만료되지 않은 기존 관측으로 계산한다. 수집기가 없는 브로커에서는 재확인을 건너뛴다.

재확인 요청의 대기열은 1개로 제한한다. 시작 전에 호출자가 취소하거나 제한 시간이 지난 요청은 수집·전송하지 않는다. 시작한 요청은 호출자의 3초 대기와 수명을 분리하므로, 취소 직후 다음 업로드가 이를 추월하지 않는다. 브로커 종료 시 수집기와 대기 중인 재확인도 종료한다.

HTTP 자체의 제한 시간(기본 5초)을 넘기거나 연결이 끊기면 서버 반영 여부는 불명이다. 이때 서버에 남은 이전 요청은 이미 지난 revision을 가지고 있으므로, 그 사이 최신 목록이 저장됐다면 412로 거절된다. 반대로 이전 요청이 먼저 반영되면 다음 업로드가 충돌을 감지하고 revision과 Git을 다시 읽어 최신 목록을 보낸다.

## 팀 의존성 분석과의 관계

팀 의존성 분석(client #110)의 3초 주기 전송(`/dependency-graph/working-files/{repoKey}`)은 이 수집기로 옮겼다. 감지 방식(3초 확인, 바뀌면 즉시 전송, 30초마다 재전송)은 같다. 의존성 그래프 태스크 안에서는 `dependencyRemote`가 있을 때만 동작하고 `find_agent`가 부를 수 없어서 분리했다. 같은 행을 두 곳에서 따로 보내면 오래된 목록이 새 목록을 덮을 수 있으므로 전송은 이 수집기 한 곳에서만 한다. 중앙은 두 경로를 같은 `working_files` 행으로 처리하므로 의존성 트리는 이 수집기의 관측을 그대로 읽는다. 의존성 그래프 업로드(60초)는 `dependencyRemote`가 설정된 경우에만 계속 동작한다.
