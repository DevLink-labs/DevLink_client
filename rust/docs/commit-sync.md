# 커밋 이력 동기화 (IDX-3-01)

2026-11-10 (Asia/Seoul), S15P31D108-185. 브로커가 바인딩된 프로젝트의 커밋 이력을 중앙에 올린다. 담당 Agent 탐색(FIND-3-01)은 이 이력으로 "최근 수정" 근거를 계산한다. 업로드 본문은 [Git 수집 범위 제한](git-collection-scope.md)의 `CommitBatch`로 만들고, 작성자는 [Git 이메일 판별](git-identity.md)의 `IdentityCache`로 정한다.

## 동작

- 브로커가 시작될 때 바인딩된 Agent 프로필이 있으면 동기화를 시작한다. 원격·저장소 키 규칙은 [작업 파일 수집](working-files.md)과 같다(`dependencyRemote`, 비어 있으면 `origin`). Git 저장소가 아니거나 원격을 찾지 못하면 한 번 알리고 동기화하지 않는다.
- 시작 직후, 이후 60초마다 `HEAD`에서 도달하는 병합 제외 커밋 중 마지막 체크포인트 이후의 범위를 정한다. 커밋이 없는 저장소나 체크포인트가 `HEAD`와 같으면 보내지 않는다.
- 커밋 시각이 최근 90일 안인 커밋만 보낸다. 중앙 추천이 최근 90일 커밋만 쓰기 때문이다(`RecommendationScorePolicy.COMMIT_WINDOW`). 개수 제한은 없다. 범위 안의 커밋은 첫 동기화든 이후 동기화든 모두 보낸다.
- 범위는 `git rev-list --no-merges --topo-order --reverse --since-as-filter`로 오래된 순서대로 정하고, 1,000개씩 `git log --no-walk --name-status -z`로 파일 목록을 읽는다. 날짜는 거르기만 한다. `--since`는 시계가 틀린 PC에서 만든 오래된 시각의 커밋을 만나면 그 이전의 최근 커밋까지 빼기 때문이다. `--since-as-filter`가 없는 Git(2.37 미만)에서만 `--since`를 쓴다.
- 파일 목록은 사용자 Git 설정과 관계없이 같아야 한다. 중앙은 같은 SHA에 다른 파일 목록이 오면 `COMMIT_CONTENT_MISMATCH`로 거부하기 때문이다. 그래서 다음을 고정한다.
  - 루트 커밋의 파일 표시(`--root`, `log.showRoot` 무시)
  - 이름 변경 탐지(`-M`, `-l1000`)
  - 경로 인용 해제(`core.quotePath=false`)
  - 외부 diff·서명 표시 끔
- `POST /api/v1/teams/{teamId}/git/commits:batch`로 보낸다. 배치는 커밋 100개, 본문 128KiB 이하다. 배치마다 중앙 연결 상태(Connected, 신원 일치)를 다시 확인한다.

## 체크포인트

- 위치는 프로필 상태 폴더의 `.devlink-runtime/commit-sync.json`(비공개 파일)이다. 스키마 버전, 서버 주소, 팀·사용자 ID, 저장소 키, 커밋 SHA, 작성자 판별 기준만 담는다.
- 서버 주소·팀·사용자·저장소 키 중 하나라도 다르면 체크포인트를 쓰지 않고 90일 범위를 처음부터 보낸다. 같은 프로필을 다른 팀이나 서버로 다시 연결해도 새 팀에 이력이 올라간다.
- 1,000개 묶음의 모든 배치가 응답을 받으면 그 묶음의 마지막 커밋을 체크포인트로 저장하고, 범위 전체가 끝나면 `HEAD`를 저장한다. 위상 순서라 어떤 커밋의 조상은 모두 그보다 앞에 오므로, 중간 체크포인트부터 다시 시작해도 빠지는 커밋이 없다.
- 전송 실패, 401·403·5xx 같은 응답, 도중 연결 끊김이면 그 묶음의 체크포인트를 저장하지 않고 다음 주기에 다시 보낸다. 중앙은 팀·저장소·SHA로 중복을 제거한다.
- 400·413은 같은 본문이 다시 거부되므로 그 배치를 건너뛰고 진행한다. 커밋 하나만으로 128KiB를 넘는 경우도 건너뛴다. 중앙이 성공 응답 안에 알린 충돌 커밋도 다시 보내지 않는다.
- 기록 재작성으로 체크포인트 커밋이 사라지면 90일 범위를 다시 보낸다.
- 연속 실패 중에는 stderr에 한 번만 알린다.

## 작성자

- 작성자는 바인딩된 사용자 본인 userId 또는 `null`(미확인)이다. 등록된 Git 이메일과 커밋 작성자 이메일의 해시가 같을 때만 본인이다. 이메일 원문은 보내지 않는다.
- Git 이메일 판별이 아직 오지 않았거나 만료(30초)됐으면 보내지 않고 5초 뒤 다시 확인한다. 판별 전에 보내 본인 커밋이 미확인으로 저장되는 것을 막는다.
- 한 번의 동기화는 시작할 때 받은 판별 결과 하나(`IdentityCache::check`)로 모든 커밋의 작성자와 체크포인트 기준을 정한다. 수집 도중 캐시가 만료되거나 비워져도 본인 커밋이 `null`로 섞이지 않는다.
- 체크포인트에는 범위를 판별한 기준(미등록, 또는 userId·이메일 해시의 지문)을 저장한다. 기준이 바뀌면(이메일 등록·변경) 90일 범위를 다시 보낸다. 중앙은 `null`로 저장한 작성자를 본인 userId로 채운다. 이미 본인으로 저장된 커밋은 바꾸지 않는다.

## 검증

- `cargo test -p devlink-broker --lib commit_sync`(실제 Git 저장소와 모의 중앙)
  - 첫 전송: 본인·미확인 작성자, 오래된 순서, 허용 키만 포함, `log.showRoot=false`에서도 루트 커밋 파일 포함
  - 이후에는 새 커밋만 전송
  - 모든 배치가 응답받기 전에는 체크포인트를 저장하지 않음, 400·413 배치만 건너뜀
  - 90일 밖 커밋 제외, 그 앞의 최근 커밋은 포함
  - 묶음별 체크포인트: 세 번째 묶음이 실패하면 다음 주기에 그 묶음만 보내고, 묶음보다 큰 새 범위도 모두 보냄
  - 같은 프로필에서 다른 팀·서버로 바꾸면 다시 전송
  - 작성자 판별이 바뀌거나 체크포인트가 사라지면 재전송
- `cargo test -p devlink-broker --lib dependency_graph::git`: `git log -z` 레코드 해석(이름 변경의 새 경로, 빈 이메일), 원격 URL 정규화.
- `cargo test -p devlink-broker --lib git_identity`
  - 미확인·미등록·등록 상태 구분과 이메일 비노출
  - 꺼낸 판별 결과는 캐시가 만료되거나 비워져도 유지됨
- 2026-11-10 로컬 중앙(Docker)과 실제 브로커(release CLI, 데스크톱 연결 절차)로 확인했다.
  - 저장소: `log.showRoot=false` 설정, 커밋 4개(본인 루트 커밋, 커밋 시각이 2020년인 본인 커밋, 팀원 커밋, 본인 커밋).
  - 연결하자 바로 3개가 올라갔다. 루트 커밋은 파일(`src/a.ts`, `ADDED`)과 함께 올라갔고, 2020년 커밋만 빠졌다. 이메일 미등록이라 작성자는 모두 `null`이었다.
  - `git-identity register` 35초 뒤 본인 커밋 2개만 본인 userId로 채워졌고, 팀원 커밋은 `null`로 남았다.
  - 새 커밋은 52초 뒤 본인 작성자·파일(`src/c.ts`, `ADDED`)과 함께 올라갔다. 체크포인트 파일에는 서버 주소·팀·사용자 ID·저장소 키·SHA·판별 지문만 있고 이메일은 없었다.
  - 같은 프로젝트를 두 번째 팀에 연결한 뒤, 그 팀의 커밋 행을 지우고 첫 팀의 체크포인트를 복사해 브로커를 다시 시작했다. 1초 안에 4개가 모두 두 번째 팀으로 다시 올라갔고, 체크포인트는 두 번째 팀 ID로 바뀌었다.
